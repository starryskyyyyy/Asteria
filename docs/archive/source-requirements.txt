**可行，而且你提出的两个协作场景都可以实现。** 这个软件可以定位为“Windows 多智能体工作台”：你在图形界面输入任务，软件启动和管理各个 CLI，把任务交给对应模型，并展示它们之间的消息、执行输出和工具调用。

最重要的设计原则是：**各 CLI 负责自己的模型执行流程，软件负责团队协作和过程展示。**

我核实了当前官方文档和项目仓库中的接口；下面是可行性判断和初步开发计划，尚未在你电脑上的具体版本中联调。

我查到的接入条件如下：

| CLI | 建议接入方式 | 已有的基础能力 |
|---|---|---|
| Codex | `codex app-server` | 创建会话、发送任务、接收执行事件、处理审批、发现模型。[ChatGPT Learn](https://developers.openai.com/codex/app-server?utm_source=chatgpt.com) |
| Claude Code | Agent SDK，或 CLI 的 `stream-json` 模式 | 保留 Claude Code 的工具与执行循环，程序化发送任务并接收文本、工具调用等事件。[Claude Code Docs](https://code.claude.com/docs/en/headless?utm_source=chatgpt.com) |
| DeepSeek Harness | SDK 或 ACP 接口 | 启动完整 Harness、管理会话、发送任务、订阅事件；仓库提供 TypeScript SDK。[GitHub](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/client/README.md?utm_source=chatgpt.com) |

这意味着，你希望的“模型仍在自己 CLI 的框架下工作”有现成的技术基础。

不过，**能够接入，不代表所有 CLI 都支持完全相同的控制功能。** 例如，目前 DSH 的 SDK 文档明确列出：没有回合中途取消接口，取消需要关闭运行进程；交互审批的部分协议能力也尚未实现。这需要在适配层中明确处理。[GitHub](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/README.md?utm_source=chatgpt.com)

你举的两类团队可以这样配置：

| 团队 | 策划与审核 | 执行 |
|---|---|---|
| 跨 CLI | Codex 会话 A，选择 GPT-6.1 Sol | DSH 会话 B，选择你指定的 DeepSeek 模型 |
| 同 CLI、不同模型 | Codex 会话 A，选择 GPT-6.1 Sol | Codex 会话 B，选择 GPT-6 Luna |

**同一个 CLI 可以创建多个独立智能体。** 每个智能体分别保存角色、模型、会话和工作目录，拥有各自的上下文。

具体模型能否使用，要以本机 CLI、模型提供方和账号权限为准。软件应动态读取模型选项，并通过实际请求验证访问能力；模型列表本身不一定代表账号已获得权限。[OpenAI Developers](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server?utm_source=chatgpt.com)

软件的核心应是一个“协作调度器”。一次工作可以按下面的流程运行：

```mermaid
flowchart TD
    A["你提交任务"] --> B["策划智能体制定方案"]
    B --> C["调度器分派任务和验收标准"]
    C --> D["执行智能体修改文件并测试"]
    D --> E["审核智能体检查结果"]
    E --> F{"是否通过"}
    F -->|通过| G["展示成果"]
    F -->|需要修改| H["生成修改任务"]
    H --> D
```

这里需要区分两个功能：

- **自动交接任务**：软件把策划结果交给执行者，再把执行结果交给审核者。这个适合首版。
- **智能体主动交流**：策划者主动选择执行者，执行者主动提问、请求帮助。可以通过团队工具实现，适合随后扩展。

例如，后续可以提供 `分派任务`、`发送消息`、`查询任务状态` 等工具，让模型自行使用。软件负责投递、记录和控制轮次。

每次交接应包含任务编号、目标、相关文件、文件版本、验收标准和结果。这样审核者才能知道执行者完成了什么，也能避免交流内容逐渐偏离原始任务。

你最关注的透明度，应当从第一版就做进去。界面建议包含：

| 区域 | 展示内容 |
|---|---|
| 团队列表 | 每个智能体的 CLI、模型、角色、当前状态 |
| 团队消息流 | 谁向谁发送了什么任务或问题，是否已投递、是否已完成 |
| 智能体详情 | 模型输出、工具名称、调用参数、返回结果、命令输出 |
| 文件变更 | 修改了哪些文件、具体差异、测试结果 |
| 操作区 | 补充要求、停止任务，以及后端支持的审批操作 |

**团队消息和工具调用都应该能点开查看原始内容。** 日志还要记录智能体、会话、任务和调用之间的关联，方便你追查“这一步是谁要求做的”。

可展示的内容取决于 CLI 实际公开的事件；模型未公开的内部推理无法保证展示。

实现上，我建议首版采用 **Electron + React + TypeScript + SQLite**：

| 模块 | 作用 |
|---|---|
| Electron、React | Windows 窗口和交互界面 |
| CLI 适配器 | 分别对接 Codex、Claude Code、DSH 的接口 |
| 协作调度器 | 分派任务、投递消息、跟踪状态、控制重试和轮次 |
| SQLite 与日志文件 | 保存团队配置、任务、消息和执行记录 |
| 工作区管理器 | 管理项目目录、文件变更和 Git 分支 |

选择 Electron 的理由是，它能同时承载网页界面和 Node.js 后台，适合管理这些本地进程。Electron 官方也提供多进程和进程通信机制。[Electron](https://www.electronjs.org/docs/latest/tutorial/process-model?utm_source=chatgpt.com)

计划可以分五步推进：

1. **先验证 Codex 与 DSH 的真实接口。**  
   在你的 Windows 环境中分别发送一个小任务，验证模型选择、流式输出、工具事件、会话恢复和停止行为。同时检查程序化模式是否正确加载你已有的配置、Skills、MCP 和登录信息。产出一份按版本记录的能力表。

2. **做单智能体工作台。**  
   先接入 Codex，实现选择项目、输入任务、查看输出和工具调用、保存历史。验收目标是：你可以在窗口里完成一次真实修改，并看清执行过程。

3. **实现 Codex → DSH → Codex 的闭环。**  
   Codex 制定方案，DSH 执行，Codex 审核；支持自动返工，并设置最大轮次、超时和失败状态。验收目标是：提交一次任务后，能自动完成整个流程，所有交接都可查看。

4. **增加团队配置与其他 CLI。**  
   支持把执行者改成另一个 Codex 会话，验证不同模型协作；再加入 Claude Code。随后增加智能体主动发消息、提问和请求分工的团队工具。

5. **完善 Windows 日常使用体验。**  
   处理中文与空格路径、进程退出、长日志、断线、软件重启和安装包。恢复历史时，要区分“查看记录”“恢复会话”“重新执行操作”，防止重复修改文件。

整个项目中，有三件事需要特别认真设计：

- **文件修改协调。** 首版安排一个执行者写文件；多个执行者并行时，使用独立 Git worktree，再统一审核与合并。
- **消息与上下文控制。** 给智能体转交相关任务、结果和文件引用，并限制自动往返轮数。
- **接口兼容性。** 各适配器声明自己支持哪些能力，固定经过验证的 CLI 版本，升级后重新检查。

**我建议第一个版本就聚焦：两名智能体、Codex 与 DSH、策划—执行—审核闭环，以及完整可查看的消息和工具记录。** 这已经能直接解决你最在意的协作透明度问题，也能为随后接入更多 CLI 留出清楚的扩展位置。
